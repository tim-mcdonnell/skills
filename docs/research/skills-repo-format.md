# Formatting this repo for public consumption

Dig findings, 2026-07-29.
Ground truth repos, cloned to the dig cache:

- `vercel-labs/skills` (the `npx skills` CLI, npm package `skills` v1.5.20) at commit `e173b8c`
- `mattpocock/skills` (reference public skills repo) at commit `2ab9580`

All citations are `path:line` within those clones at those commits.

## Question 1: Is our flat `<skill>/SKILL.md` layout compatible with `npx skills`?

Yes, as-is.

`discoverSkills()` scans a priority list of directories whose first entry is the repo root itself, and checks every immediate child directory for a `SKILL.md` (`src/skills.ts:246-253`, `src/skills.ts:277-291` at `e173b8c`).
So `dig/SKILL.md` at repo root is found without any `skills/` or `.claude/skills/` wrapper.
A recursive fallback walk (depth 5) covers anything the priority dirs miss (`src/skills.ts:311-323`).

Frontmatter requirements are exactly two string fields: `name` and `description` (`src/skills.ts:95-110`).
No length limits, no format validation, no `license`/`version`/`metadata` required.
The install directory is named from frontmatter `name`, not the folder name (`src/installer.ts:286-287`), and duplicate `name`s across a repo are silently dropped after the first (`src/skills.ts:269-274`).

Install commands consumers will run:

```
npx skills add <owner>/skills          # whole repo
npx skills add <owner>/skills@dig      # just the dig skill
```

`skills update` tracks changes by content hash, not a version field (`src/local-lock.ts:34-39`), so no versioning metadata is needed inside skills.
`npx skills find` queries the hosted skills.sh index (`src/find.ts:17,86-91`); the CLI contains no crawler, so listing there just requires the repo to be public.

## Question 2: What do OpenAI models / the Codex harness need?

Nothing is required; one small addition is worth copying.

The CLI treats Codex as a "universal" agent: skills install byte-for-byte into the shared `.agents/skills` directory (project) or `~/.agents/skills` (global) with no transformation - no AGENTS.md generation, no prompts folder, no `config.toml` edits (`src/agents.ts:203-211`, `src/installer.ts:121-149`, `src/installer.ts:462-514` at `e173b8c`).
Plain `name`/`description` frontmatter works identically in Claude Code and Codex.

What mattpocock/skills adds on top, present in 41 of 41 skills: an `agents/openai.yaml` beside each `SKILL.md` carrying Codex UI metadata - `interface.display_name` and `interface.short_description` for the Codex skill picker, plus `policy.allow_implicit_invocation: false` mirroring `disable-model-invocation` for user-invoked skills (e.g. `skills/engineering/tdd/agents/openai.yaml`, `skills/engineering/implement/agents/openai.yaml` at `2ab9580`).
The sync rule is stated at `.agents/invocation.md:10`: a skill is user-invoked in both harnesses or neither.

Also worth copying: `AGENTS.md` as a symlink to `CLAUDE.md` at repo root, so one rules file serves both the Claude convention and the generic-agent convention (confirmed symlink at `2ab9580`).

## Question 3: Documentation conventions

From mattpocock/skills at `2ab9580`:

- Top-level `README.md` leads with a 30-second install section split by audience (Claude Code plugin, Codex/other agents via `npx skills`, tinkerers who want editable files), then a reference index listing every promoted skill grouped by invocation mode with one-line descriptions (`README.md:25-82`, `README.md:184-228`).
- `LICENSE` is MIT.
- `CHANGELOG.md` is generated by Changesets (`.changeset/config.json:2-5`); the only CI workflow opens Version Packages PRs (`.github/workflows/release.yml:29-37`).
- Promoted skills each get an external docs page under `docs/<bucket>/<skill>.md` with a fixed template (`.agents/writing-docs.md:15-64`); links must be absolute because pages are republished off-repo.
- No CONTRIBUTING.md and no issue templates exist; the repo runs on a terse `CLAUDE.md` (24 lines) of invariants instead.

## Question 4: Everything else observed

Worth stealing when this repo grows:

- Bucket dirs (`skills/engineering/`, `skills/misc/`, `skills/in-progress/`, `skills/deprecated/`) with "promoted" invariants: a promoted skill must appear in README and the plugin manifest, non-promoted must appear in neither (`CLAUDE.md:1-10`).
- `.claude-plugin/plugin.json` + `marketplace.json` make the repo installable as a Claude Code plugin and self-host as a marketplace; the CLI also reads these for nicer grouping (`src/plugin-manifest.ts:51-183` at `e173b8c`).
- `.out-of-scope/` directory logging rejected feature requests with rationale and the GitHub issue number that prompted each.
- A router skill (`ask-matt`) with a self-maintenance trigger in `CLAUDE.md:22`: renaming any skill forces a router re-sync, "a router that lies" otherwise.
- Per-term `_Avoid_:` synonym bans in glossaries to force one canonical term repo-wide (`skills/productivity/writing-great-skills/GLOSSARY.md:12-29`).

Mistakes observed, to avoid:

- Link rot after a skill rename (`docs/engineering/research.md:29` still points at the retired `to-prd` name) - nothing automated catches it.
- Version number duplicated between `package.json` and `.claude-plugin/plugin.json`, manually synced and already out of sync at HEAD (1.1.0 vs 1.2.0).
- No CI validation of skills at all (no frontmatter lint, no `claude plugin validate --strict` in CI); the invariants hold by discipline alone.
